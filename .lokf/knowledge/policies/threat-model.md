# Overview

The page was added on 2026-09-14, when the design moved out of `SECURITY.md`. It is the shared threat model for every repository in the lmodel organisation and for seven repositories of the noelmcloughlin account: `ktl-federation`, `linkmo`, `ai-linkmo`, `linkml-sidecar` and the three KTL repositories (`knowledge-trust-ladder`, KTL Registrar, KTL Curator). Each of them has a `SECURITY.md` that says how to report a vulnerability, what that repository owns, and which measures on the page it carries. A reader reads that file first, and the page for the reasoning behind it.[^docs-threat-model.md] `scripts/validate-repository.sh` check 9 records this path and six of its headings, the sync workflow's and the website's among them, as ones a sibling depends on.

The repositories share how they are built and released. Workflows start with no permissions and pin their actions to commits, releases are cut only from `main` behind an Environment, and each file a release attaches carries a signed build provenance. No agent runs in any of that. Most of the repositories also carry a knowledge bundle under `.lokf/`, kept by workflows copied from `ktl-sidecar`'s templates. The page's *Knowledge bundles and skills* part covers those workflows and the skills that work on a bundle, which is where an agent runs. A repository's own `SECURITY.md` or threat model covers what it runs beyond these: an application, a project generated from a template, or the workflows a fork carries from its upstream project.[^docs-threat-model.md]

**Schema builds and releases.** A schema repository in the lmodel organisation runs these workflows beside the knowledge-bundle ones, and no LLM, AI agent or AI tool runs in any of them. The build and test workflow, `main.yaml`, only reads: it runs with `contents: read` and `persist-credentials: false`, installs the project with `uv sync --locked`, lints the schema, checks that the generated files match it, and runs the tests. `semantic-release.yml` previews each pull request with `--dry-run`, which writes nothing, and its `release` job runs only on a push to `main`, in the `release` Environment.[^docs-threat-model.md]

A schema repository's release is a GitHub Release, not a package. `knowledge-release.yaml` attaches the domain vocabulary as `schema-<tag>-<name>.yaml`, the knowledge bundle as a zip, its evidence table as `evidence-<tag>-<name>.tsv` and any Microsoft 365 Copilot skill as a zip, each with its `.sha256` file and a signed build provenance. No repository publishes to PyPI: two carry `pypi-publish.yaml`, which stays off until the repository variable `PYPI_RELEASE_ENABLED` is `true`, and neither sets it. Where a repository attaches a LOKF copy of its schema (`lokf-copy-release.yaml`), a read-only `build` job checks the copy, and only a separate `attach` job can write. `upstream-watch.yaml` runs weekly and by hand, never on a pull request, and its only write is to open or comment on an issue.[^docs-threat-model.md]

**Interactive use is advisory, not enforced.** A skill's `Scope:` line is prose, not a checked permission. An agent run interactively has whatever access its harness grants, and only the scheduled `knowledge-librarian.yaml` enforces its scope, because nothing is watching it run.

The skills ktl-curator, ktl-librarian, ktl-prose, ktl-sidecar and ktl-website also run the repository's scripts from `.lokf/scripts/`. Anyone who can commit to the repository can change those scripts, so a skill runs them as the repository's code. ktl-website's build also runs `site.config.mjs`, the site's files under `website/`, and the commands `site.config.mjs` names, or a `gen-doc` recipe it finds, to build the schema's pages and the data, and they are the repository's code too. The preflight's `copies` line cannot check them, because the preflight is one of them.

Since 2026-10-05, ktl-docent runs none of them. It runs its own copies of `knowledge-report.sh` and `knowledge-feedback.sh`, which a check in `knowledge-trust-ladder` holds byte-identical to their templates, so a question runs no code the repository supplies. That holds only where the skill comes from a source the reader trusts, since a repository that holds its own copy of a skill supplies the instructions and the scripts.

**Repository hardening**:

- Actions are pinned to commit SHAs everywhere, including the seven workflow templates under `skills/ktl-sidecar/templates/github/` and `skills/ktl-website/templates/github/`. Dependabot bumps the workflow pins, and the templates are bumped by hand, since Dependabot scans only `.github/workflows/`.
- `permissions: {}` is at the top of every workflow.
- The agent step runs the reviewed, in-repo wrapper, never a repository variable's content as a command. `AGENT_CLI` chooses the agent, `KNOWLEDGE_LIBRARIAN_ENABLED` turns it on, and the workflow triggers only on `schedule` and `workflow_dispatch`. A domain host's members script takes the job token as `KNOWLEDGE_FEDERATE_TOKEN`, removes it from its own environment, and hands it to `gh` alone, to verify attestations.
- harden-runner runs in audit mode as the first step of every job.
- Release files carry a signed build provenance. `knowledge-release.yaml` writes a `.sha256` file beside each file it attaches, and an attestation of the file's build provenance, signed by the release workflow. The Obsidian plugins' `release.yml` attests `main.js` and `styles.css` and opens a draft release that a person publishes. Anyone can check a file with `gh attestation verify`.
- The librarian is split into four jobs, so the write token and the agent never meet. The `earlier` job's token can read pull requests and nothing else. The read-only `refresh` job runs the agent and hands on the patch file the agent wrote, and nothing it made from it. The `apply` job, under `contents: read` on a runner the agent never shared, writes that file with the default branch's pen and toolkit, validates the result and hands it on as a patch. Only the agent-free `publish` job can write. The agent's one credential is the `AGENT_API_KEY` secret or, with `AGENT_USE_JOB_TOKEN`, the job's own token, holding `contents: read` and `copilot-requests: write`. It is exported into the agent's environment only, under a credential-shaped name the wrapper checks (2026-09-24).
- Every secret lives in an Environment limited to the default branch. The librarian's agent key, the sync token and the ingest credentials each belong in the Environment of the one workflow that reads them, `knowledge-librarian`, `knowledge-sync` or `knowledge-ingest`, since a repository secret can be read by a workflow on any branch, and a workflow file runs on a push to the branch that carries it, with a `permissions:` key that can raise its own token. The templates still read a same-named repository secret too, so a host works while it moves them. Every host should move them. A private repository on GitHub Free has no Environments, and its secrets stay readable from any branch there.
- A host's sync runs no code from the release, and the branch it pushes carries no workflow the release wrote. `knowledge-sync.yaml`'s `sync` job reads the release as data, under `contents: read` and with no git credential on disk. Its `publish` job applies only the copies, the pin and the changelog, and holds the release's workflow changes for a person.
- The release workflow is split the same way (2026-09-24). A `pack` job installs the toolkit and validates under `contents: read`. An `attach` job runs no third-party packages, holds `contents: write`, and checks each file, the bundle's zip, the domain vocabulary, the evidence table and any Copilot skill's zip, against the checksum `pack` made before it attests and uploads it. The release step, the sidecar's `knowledge-sync.sh` and its `knowledge-sync.yaml` workflow move the skill pin together.
- No agent's job saves a cache that a trusted job restores. setup-uv saves its cache under a key that names no job, and uv trusts the wheels it unpacked there without hashing them again. So the jobs that run an agent, the librarian's `refresh` and `docent-eval.yml`, take no uv cache and no npm cache. The jobs whose result is trusted take no uv cache either: the librarian's `apply`, the release's `pack`, the registrar's gate and `knowledge-trust-ladder`'s `publish.yml`.
- A domain host's federation build reads the members' releases and never runs them. It fetches only the files the member concepts name, over http or https from a public address. A local path needs `--allow-local`, and a private address needs a person's `private_addresses: allow` on the Domain concept, which a pull request's check does not take as it stands. Each connection to a member checks the address it opens, so a name that answers a public address to the check and a private one to the connection (DNS rebinding) reaches nothing. Through a proxy, the proxy resolves each name that the federation build and the ingest fetch, so only the check before the request applies, and the proxy must refuse a private address itself. Neither checks a name that resolves only at the proxy, and the ingest's git uses the proxy the ingest chose, or none, whatever git's own configuration says.[^docs-threat-model.md] Every address that is not public counts as private, the shared address space 100.64.0.0/10 among them. It checks each file against the checksum a person confirmed. For a GitHub release it checks the attestation too, signed by the member's own release workflow, and it stops without `gh`. It refuses a zip holding a symbolic link, a path outside its root, a hidden file such as a `.git` folder, a file a browser runs, or more than a size limit unpacked. It also refuses a distribution name that is not one plain file name. It runs the host's report on each member with git pointed at no repository. A member of a member is confirmed by that member domain, not by the host's person, so it brings content, not code. Its `check` and `build` jobs hold a read token, which reaches `gh` alone. Only `publish` can write, and it checks the workspace zip against the checksum `build` wrote, which catches a fault in the transfer: `build` decides what `publish` signs.
- Every workflow write to `main` waits for the `release` Environment. Its required reviewers must be configured by hand, or the Environment exists in name only. Release tooling is installed with `npm install --ignore-scripts`.
- The skills release runs its checks in a job that cannot write. In `knowledge-trust-ladder`, `publish.yml`'s `verify` job runs the contract and the test suite, with the packages the tests install, under `contents: read`. The `publish` job needs it and holds the write token, and runs neither. `tests/requirements.txt` is compiled from `tests/requirements.in` with every hash, and that job and `validate.yml` install it with `uv pip install --require-hashes`, since `uv run --with-requirements` checks none.
- `main` blocks deletion, force-pushes and non-linear history, and nothing more, since a stricter ruleset would also reject the release job's commit.
- Secret scanning and push protection are on. They are GitHub settings nothing in CI can assert, so keeping them on is a maintainer responsibility.
- No tracked file holds a character a reader cannot see, which `knowledge-trust-ladder`'s contract checks (2026-10-04).
- CodeQL and dependency review are skipped where there is nothing for them to scan.
- The skill a scheduled run installs is pinned to a commit: the install step installs nothing unless the release tag still names the commit it named when the pin was set.
- Every workflow that installs the lokf toolkit does so with `uv sync --locked`. So each file is checked against the hash `.lokf/uv.lock` records, and a lock that is missing or out of date fails the job.
- The Python halves of the conventions script and the pen name one PyYAML release, and take no file uploaded after a set date.
- Where there is no Python, ktl-librarian and ktl-sidecar read LOKF's schema from GitHub by commit, never by tag, so the file cannot change under them (2026-10-05). The contract in `knowledge-trust-ladder` fails a tag or a branch in that URL, and two pages that pin different commits.

**The sync workflow** keeps a host's sidecar and site copies, and its skill pin, at the newest release, and runs no agent. Its `sync` job clones the release without a checkout and copies only what `knowledge-sync.manifest` names. It refuses a copy path outside the host's tree or inside a `.git` folder, where a copy would be git's own configuration, which can name a command git runs. Its `publish` job runs the default branch's copy of `knowledge-sync.sh --apply`. That refuses a patch that touches anything but the sidecar's copies, the site's copies, the pin and the changelog. It also refuses a path with a character outside the plain set the templates use, and a deletion, a rename, a link or an unusual mode. It keeps every workflow as the default branch has it and sets the pin itself.

The branch the sync pushes carries no workflow the release wrote, since a workflow on the pushed branch would run before review, with the repository's secrets and a token it can raise. A person applies the held workflow changes after reading them, or approves them in a review Environment with required reviewers, after which a job pushes them. `KNOWLEDGE_SYNC_TOKEN`, scoped to Contents, Pull requests and Workflows for that repository alone and kept in the `knowledge-sync` Environment, reaches the `publish` and `push-workflows` jobs alone. It lets them push one branch, `knowledge-sync`, and open or edit one pull request, which a person reviews before the pin moves. Its force-push touches only that branch, leased to the commit the `earlier` job read, so a commit added since is never lost.

The `earlier` job first reads the committers on the branch, and leaves alone a branch a person added a commit to. A committer's name is a claim, so this check protects a person's work from the force-push and does not stop an attacker. A repository that gates merges on approvals should dismiss stale approvals when the branch changes.

Run by hand, the script copies the workflows too, and runs the sidecar's checks on the synced copies unless given `--no-checks`, so a person who syncs that way runs the release's code on their own machine.

**The website** is built by `knowledge-website.yaml`'s `build` job, which runs npm's packages, the lokf toolkit, `just` and the repository's own code: `site.config.mjs`, the files under `website/`, and the commands that build the schema's pages and the data. It holds a read-only token and no secret. `npm ci --ignore-scripts` runs no package's install script, and Astro's telemetry is off. Its `deploy` job runs harden-runner and GitHub's deploy action, on the default branch alone, once the repository variable is set, in the `github-pages` Environment, which GitHub limits to the default branch. A pull request's build runs that pull request's code, as any check does, and anyone who can read the repository can download its artifact.

The sync copies a file only when it is inside the repository, and follows a link only when the link ends inside it. An SVG that holds a script, an event handler or a `javascript:` address is left out. Raw HTML in the Markdown passes as GitHub renders a README. A tag GitHub allows keeps the attributes it allows, an address that is not http, https, mailto, a path or a fragment is dropped, and anything else is shown as text. A project site shares its origin with every other project site of its owner, so a script on one would run with all of them. A private repository should set harden-runner's egress policy to `block` in the `build` job, with the package registries allowed. `BROWSE` publishes its databases whole, and is off unless `site.config.mjs` turns it on.

**The ingest workflow**, `knowledge-ingest.yaml`, mirrors the sources `.lokf/ingest.yaml` names, from outside the repository, into `.lokf/mirror/`. No LLM, AI agent or AI tool runs in it. What it fetches reaches the scheduled librarian only after a person merges the pull request, so the mirror has the same standing as any other repository content: reviewed before an agent reads it. Its shape answers four findings a reader may raise.[^docs-threat-model.md]

- **It fetches content at run time.** It fetches only from the addresses the manifest names, in a job under `contents: read` with no git credential on disk. The script caps each body, in size and in time, each file it writes, and the mirror as a whole. It refuses an address that is not public unless the manifest allows it, at each connection as well as before the request, so DNS rebinding cannot reach one, except through a proxy, as for the federation build. It also refuses a content type the entry does not expect. It drops the credential on a redirect to another host, port or scheme, and removes every character a reader cannot see, apart from the joiners that Persian, Arabic and Indic scripts and emoji spell with. What leaves the job is a patch of Markdown files and the lock.
- **It runs git and the host's own commands.** A `git` entry names an https address, or http and a local path where the manifest allows private addresses. Git takes its protocol limits and the credential, scoped to that address, from its environment, which needs git 2.31. It follows no redirect with a credential, or where the manifest refuses private addresses. Where the manifest refuses private addresses, unless a proxy resolves the name, it connects only to the addresses the check found, which needs git 2.37 for a `git` entry that names a host. The script refuses an address that git's own configuration rewrites, by `url.<base>.insteadOf`, since the check does not cover it.

  A `command` entry runs only a command the host committed, with no shell and a clean environment. Outside a git work tree nothing can check that, so the command runs and its lock record carries `command_unchecked`; in a repository git will not read, one another user owns for instance, it is refused instead. It runs as the script's user, so the credentials it is not given are withheld as a courtesy, not by a boundary: a command is reviewed code, as any file in the repository is.
- **It holds secrets.** The manifest names each credential as an environment variable starting `KNOWLEDGE_INGEST_`, and the job hands over the repository secrets of those names and no other. Git gets no other credential: it runs with a home folder of its own, so curl reads no `~/.netrc`. The script prints no value, and the lock records none, apart from the last line a failing command printed, which is the command's own. For a confidential entry, the committed lock records only how the run went, and no page's title, address or author, unless the entry sets `lock_details: true`. The job that holds the secrets has no write token, and the job that writes has no secret.
- **It force-pushes.** It does so only to `knowledge-ingest`, the workflow's own branch, only over its own single commit there, and leased to the commit the `publish` job read, so a commit added since is never lost. A branch a person committed to is left alone, with or without a pull request. The `publish` job refuses a patch that touches anything but `.lokf/mirror/` and the lock.

**The docent eval**, `docent-eval.yml` in `knowledge-trust-ladder`, runs ktl-docent on a holdout of questions through `claude plugin eval`, weekly and by hand, and never on a pull request or a push. An agent runs in it, so it has the scheduled librarian's surfaces with less at stake. The job holds `contents: read`, keeps no git credential on disk, and writes nothing to the repository: the result goes to the run's summary and a workflow artifact. Its API credential is the `AGENT_API_KEY` secret of the `docent-eval` Environment, limited to the default branch. The job checks the name that the `AGENT_API_KEY_ENV` variable gives, as the librarian's wrapper does, and exports the key under it, so the key reaches the eval's process and nothing else.

The job does nothing until the repository variable `KNOWLEDGE_DOCENT_EVAL_ENABLED` is `true`. A cost ceiling stops it before a run starts once the ceiling is spent, and a pull request from a fork cannot start it.[^docs-threat-model.md]

The questions and the concept each one expects live in `tests/docent-holdout.yaml`, outside `.lokf/`, so the docent never reads a question beside its answer. Each run starts in an empty directory, into which `evals/scaffold-bundle.sh` copies the bundle alone, without `tests/`, `evals/` or `.lokf/feedback.md`. The agent has read-only tools and no shell, as in any docent session, so a question runs no code the repository supplies. The scaffold runs as the operator, outside the agent's sandbox. It is `knowledge-trust-ladder`'s code, reviewed as any other, and the job grants the agent no further tool. A concept written to steer an eval's answer would steer the docent's readers first, and the review before merge and the curator exist to catch it.

A green run proves that the docent named the expected concept, not that an answer was right. No judge reads the answers, so nothing in them reaches a second model.

**The librarian's pen (added 2026-10-03)**: the librarian writes the bundle only through `knowledge-apply.sh`. ktl-librarian describes each change as an operation in `.lokf/patch.yaml`, and the script stamps `generated`. It refuses an operation that would name a person as its actor. It refuses to rewrite text a person wrote, or to delete a concept a person confirmed or left a note on. It writes nothing unless every operation passes. The pen also compares each concept it is about to write with the file it read. It refuses the patch when a person's event or note would differ, however the operations spelt it.

In a scheduled run the agent's one output is the patch file, and the `apply` job writes it with the default branch's pen, so the agent never writes the bundle itself. `publish` checks the patched tree for the same refusals with `knowledge-provenance.sh --unattended`. `docs/threat-model.md` lists the pen under repository hardening.

**Human attribution**: a `verified` event whose actor starts with `human:`, or a `generated` record written that way, is a claim, not a credential. It is a string in Markdown that any writer can type. The realistic threat is not an outside attacker but **another agent** driving `ktl-curator` and recording confirmations nobody gave.

`knowledge-registrar.yaml`'s `provenance` job is the authority. It requires an approving review from the named account, or their verified signature on the introducing commit: evidence GitHub holds, rather than evidence the bundle asserts. That job reads the events themselves: whole, from the frontmatter, against every parent of a commit, and keyed by the concept's `id`. So a re-dated event counts, while a rename, a merge and an example in a body code fence do not. Conventions rule 10 keeps those fields to spellings a line reader and a parser agree on.

ktl-curator writes `human:` only for an authenticated identity: `gh api user`, `glab api user`, or a signing key the forge lists under the stated login. Without one, it refuses the two verbs that assert a person vouched for something, while the three that assert nothing about who checked what stay available. It refuses to run a review session unattended, and its report flags an unsigned `human:` commit rather than trusting it silently.

`knowledge-provenance.sh` (2026-09-17) does the signature half where GitHub is not the forge, or as a second opinion where it is. It checks against public keys the repository carries under `.lokf/curators/`, one GPG or SSH key per curator id. It refuses a change that adds an id's key and that id's confirmation together. The optional `attestation` job is off unless `KNOWLEDGE_CURATION_ENVIRONMENT` names an environment, and naming one whose required reviewers are empty makes it self-approve instantly.

Where `.lokf/` is gitignored, no pull request ever carries the bundle, so the CI half never runs and the curator's in-session rules are the whole of it. A host without git has only its platform's version history. None of this proves anyone read the source: it raises the cost of forgery, not the truth of a confirmation.

**Prompt-injection guards**, one per input path, across the six skills that read content they did not author:

- ktl-librarian resolves a `.lokf/feedback.md` entry only from the source it names, never from the entry's own wording, and ktl-curator only counts the waiting entries, with `grep -c`.
- ktl-curator quotes a fetched source to a person rather than acting on it.
- ktl-docent treats fetched or repository content as text to quote, never instructions, and is read-only on the bundle besides. Since 2026-09-23 it adds a feedback entry through `knowledge-feedback.sh` (its own copy since 2026-10-05), rather than by opening `feedback.md`. So the librarian is the only skill that reads what a reader wrote. Its one write path asks once per session first. A Disagreement may name its concept, which must be a concept file in the bundle's lowercase spelling. `knowledge-report.sh` reads that path back to mark the concept disputed, and reads nothing else of the entry.
- ktl-prose never opens `.lokf/feedback.md`, and rewords only in a live session, on a request addressed to it. Its check script refuses a rewording that touches a concept a person wrote or confirmed, or a byte of frontmatter, or that adds a character no reader sees.
- The registrar's `provenance` job, which reads pull-request metadata, runs no agent. Event fields enter through `env:`, API reads are narrowed to logins, SHAs and a verification flag, and the `human:<id>` is held to a login's characters. The token is read-only, and a path git still has to quote is refused (2026-09-19).
- The librarian's `earlier` job, which lists the pull requests the workflow opened, runs no agent either and reads no title, body or comment. It counts a pull request only when its branch is `knowledge-librarian/...` in this repository, and matches each value it takes against a pattern. Only the hashes of the feedback entries those pull requests handled leave the job, since the entries are readers' words.
- A file under `.lokf/mirror/` is a copy of a page or document from outside the repository, written by the ingest and merged by a person before the librarian reads it. The librarian derives from it as from any source: text to derive from, never instructions. So a reviewer of the ingest pull request reads the diff as the source page, and the manifest decides what comes in.

If a guard fails, the only unattended write path is `knowledge-librarian.yaml`'s `publish` job. The checks that count run in `apply` and `publish`, on clean checkouts the agent never shared. `refresh` hands on only the patch file the agent wrote, which the wrapper copies out once the agent has finished. `apply` writes that file with the default branch's pen, on the toolkit `uv.lock` pins, runs `lokf validate --check-refs` and the conventions script, and packages what the pen wrote as a patch. `publish` re-derives the touched paths from that patch's own `git apply --numstat`. It confines them to `.lokf/knowledge`, `knowledge_bundle`, `.lokf/feedback.md` and `.lokf/questions.md`, the only pathspecs the patch is built from. It separately refuses a patch that adds a `by: human:` line. It refuses a patch that touches a person's record: an event added, changed or removed in any YAML layout, a person's note added or removed, or text a person wrote changed.

Inside `refresh`, the wrapper's post-run check only stops a bad run early, since an agent sharing that workspace could in principle defeat it. It could rewrite `core.fsmonitor` or `core.hooksPath`, add a rule to `.git/info/exclude` that hides its writes, or truncate the running script. Against the first two, the wrapper snapshots `.git/config`, `.git/hooks` and `.git/info` before the agent call and restores them from an `EXIT` trap, so they are restored even when the agent fails or the job is cancelled. Against the last, its checks are in a `main()` called last. It runs the pen and the gate from copies taken out of HEAD before the agent runs, and refuses a run in which the agent moved HEAD, changed those copies or changed which files git watches. Nothing on that runner is out of the agent's reach, since the agent shares the job's user. So nothing that job made from the patch file goes on, and `apply` runs the pen and the checks again where the agent never ran. The result is a pull request that never pushes to `main` and never auto-merges, and merging it is a human decision like any other change.

**A person's record is never removed without that person.** `docs/threat-model.md` says the `provenance` job collects the actor of every `human:` event a pull request adds, changes or removes. A `verified` event struck out, or gone with its concept, needs the same approval or signature as one that is added. A person's `generated` record may be replaced only by another person's.

**The ledger of readers' questions.** A handled feedback entry moves from `feedback.md` to `.lokf/questions.md`, which the pen writes and only programs read. The pen takes every character a reader cannot see out of the question it files there, and refuses a patch that handles more than ten entries. The librarian keeps a reader's words out of `log.md`, out of every concept and out of its hand-off, since the curator opens the first two and a person reads the third. From the ledger, `knowledge-report.sh` builds the one prompt of the retrieval test. An agent answers it from an empty directory, and its reply is read for concept paths only.

**The librarian's hand-off (2026-10-04).** The patch file may carry up to ten lines for the person reviewing the pull request, in the agent's own words. It is the one free text that passes from the agent to the pull request. The pen holds each line to printable text with no backtick and writes none of it to the bundle. It takes out every character a reader cannot see, as Unicode marks it, so it removes a bidirectional mark, a tag character or a variation selector as it removes a zero-width space.

The lines travel inside the patch file, and the pen in `apply` takes them out of it on a runner the agent never shared. Once the agent returns, the wrapper removes whatever is at the paths the workflow reads, the patch file's copy and the retrieval score's, so a file or a link the agent left there is gone. The retrieval test calls the agent again, with readers' words in its prompt, after the wrapper has copied the patch file. So the wrapper refuses the run when that copy changed during the call. `publish` cleans the lines again and shows them in a code block, where nothing renders, and the curator never opens a pull request body.

**A confirmation covers the text the person saw (2026-10-04).** The label *confirmed by a person* holds while `generated.at` is no later than the confirmation. The pen restamps every change it writes, and conventions rule 13 fails a pull request in which any other writer changes a confirmed concept's content and leaves `generated` as it was. Rule 14 covers the commit that records the confirmation. On a pull request, such a commit may change what the concept says only when the person is also recorded as its author, as *Correct now* records them.

**What this does not cover.** Ordinary repository content the librarian scrapes while building concepts, such as READMEs, docs and code, has no per-entry guard. It relies on the review before merge that every change to `main` goes through. Nothing in KTL filters what a reader asks `ktl-docent`, since that boundary belongs to the agent harness running the skill. Nor does any of this make a repository a sandbox. A compromised runner, upstream action or agent harness is out of reach, and a finding in one of those should still be reported to the affected repository, with scope and reproduction.

**A skills repository.** A skills repository is the case where the content the librarian scrapes is all instructions, since every `SKILL.md` is written for an agent to follow. The same guards hold there. The librarian reads each source as data, writes only `patch.yaml` through the pen, and holds `contents: read` in a scheduled run. An instruction in a source can still shape what a concept says. Only the person reviewing the pull request catches that, since the pen checks a patch's form and never its truth.
