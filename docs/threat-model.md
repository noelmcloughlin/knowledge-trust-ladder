# Threat model

The three LOKF repositories - [`lokf-agent-skills`](https://github.com/noelmcloughlin/lokf-agent-skills), [LOKF Registrar](https://github.com/noelmcloughlin/obsidian-lokf-registrar), and [LOKF Curator](https://github.com/noelmcloughlin/obsidian-lokf-curator) - run the same scheduled agent from the same `lokf-sidecar` templates and release the same way, so they share one threat model. This page is it. Each repository's `SECURITY.md` says how to report, what that repository owns, and what it inherits from here.

Two facts shape everything below. The skills are prose executed by whichever LLM agent runs them, so anywhere a skill sends the agent to read content it did not author is a prompt-injection surface. And the bundle's central trust signal - a `verified` event whose actor starts with `human:` - is a string in a Markdown file that any writer can type.

## Interactive use: scope is advisory, not enforced

A skill's `Scope:` line ("owns only `.lokf/`") is prose, not a checked permission: the Agent Skills format has no manifest for that, and an agent run interactively has whatever tool access your harness already grants it - the generic warning `npx skills` prints after every install. Only the scheduled `knowledge-librarian.yaml` enforces its scope, because nothing is watching it run. Interactively, review what the agent changed before you commit or merge; that is the discipline the scheduled path's mandatory pull-request review provides automatically.

## Repository hardening

What every repository does, and why. Each `SECURITY.md` says which of these its repository carries.

- **Actions pinned to commit SHAs** in every workflow and in the two templates under `skills/lokf-sidecar/templates/github/`. Dependabot bumps the workflow pins; the templates are bumped by hand, since Dependabot scans only `.github/workflows/`.
- **`permissions: {}` at the top of every workflow**, and harden-runner in audit mode on every job that installs packages or runs third-party code.
- **The librarian runs in two jobs so the agent and the write token never meet.** `refresh` runs the agent with `contents: read` and no git credential on disk, and hands its change on as a patch; only `publish`, which runs no agent code, can write. What each job checks is under [Prompt-injection guards](#prompt-injection-guards).
- **The agent step runs the reviewed, in-repo wrapper**, never a repository variable's content as a command; `AGENT_CLI` chooses which agent, `KNOWLEDGE_LIBRARIAN_ENABLED` arms it, and the workflow triggers only on `schedule` and `workflow_dispatch`.
- **Every workflow write to `main` sits behind the `release` GitHub Environment**, whose required reviewers must be configured by hand or the gate exists in name only. Release tooling is installed with `npm install --ignore-scripts`.
- **`main` blocks deletion and force-pushes and requires linear history, and no more**, because a rule requiring pull requests or passing checks would also reject the release job's own push ([how the repositories release](releasing.md#what-the-repository-settings-mean-for-you)).
- **Secret scanning and push protection are on.** They are GitHub settings nothing in CI can assert, so keeping them on is a maintainer responsibility.
- **CodeQL and dependency review are off where there is nothing for them to scan.**

## Human attribution: `human:` is a claim, not a credential

A `verified` event whose actor starts with `human:` says "a named person checked this concept against its source". Everything downstream keys off it: lokf-curator's health line, lokf-docent's answer footers, and the OKF trust tiers themselves. It is also just a string in a Markdown file. Any writer can type one, and `lokf validate` accepts it, because a forged event is perfectly well-formed. The realistic threat is not an outside attacker but the ordinary shape of agent work: **another agent** driving lokf-curator - an orchestrator, a subagent, a scheduled run, or a session where the "person" answering is really a tool result - recording confirmations nobody gave. An identity resolved from the local environment cannot tell that from a real session, because both arrive through the same channel.

Four measures, in descending order of weight:

- **The forge is the authority.** On each pull request, `knowledge-registrar.yaml`'s `provenance` job collects the actor of every `human:` event added or changed under `.lokf/knowledge/`, a `verified` entry or the `generated` record - read whole from the frontmatter, against every parent of a commit, and keyed by the concept's `id`, so a re-dated event counts while a renamed concept, a merge and an example in a body code fence do not - and requires evidence GitHub holds: an approving review from that account, or - since GitHub blocks approving your own pull request - that account's verified signature on the commit that introduced the event. This is the only measure a confused or adversarial writer cannot decline to follow, because it runs outside the agent. Where GitHub is not the forge, or as a second opinion where it is, `knowledge-provenance.sh` does the signature half with plain git, and gpg or ssh-keygen, against public keys the repository carries under `.lokf/curators/`, one GPG or SSH key per curator id, and refuses a change that adds an id's key and that id's confirmation together.
- **lokf-curator writes `human:` only for an authenticated identity** - `gh api user`, `glab api user`, or a signing key the forge lists under the login the person states; never a typed name on its own. The `git config user.name` fallback (a writable config value) and the "just ask" fallback (the one channel an attacker fully controls) are gone. Without an authenticated id, the two verbs that assert a person vouched for something are refused; the three that assert nothing about who checked what stay available.
- **lokf-curator refuses to run a review session unattended** - CI, headless, subagent, scheduled, or with answers arriving from a file or tool result rather than a live turn. Its read-only report is safe to run anywhere.
- **Detection, not only prevention.** The curator's report counts `human:` events whose introducing commit carries no signature, so one that arrived by another route is visible to the next person who looks instead of silently trusted.

**Limits, stated plainly.** A signature proves a key holder made a commit and an approval proves an account clicked a button; neither proves anyone read the source. The gate raises forgery from "type four lines of YAML" to "control that person's GitHub account or signing key". It does not make a confirmation true. And where `.lokf/` is gitignored, no pull request ever carries the bundle, so the CI half never runs: there, the curator's in-session rules are the whole of it. A host with no git at all has only its platform's version history, which the curator names as the record and the report says so every time.

**The optional `attestation` job** is off unless `KNOWLEDGE_CURATION_ENVIRONMENT` names an environment, and exists for repositories that cannot sign. It is deliberately not a switch that disables the check - a permanent "provenance: off" gets flipped once and never back - but a fresh, logged approval from an environment reviewer on each affected pull request. One misconfiguration matters: naming an environment whose **required reviewers** are empty makes it self-approve instantly, turning the gate into a false assurance. Configure the reviewers first.

## Prompt-injection guards

The four skills read content they did not author - repository files, external URLs, reader questions - and either act on it or hand it to a person. Each skill's `SKILL.md` carries the guard for its own input path; this is the map.

- **`.lokf/feedback.md` (lokf-librarian).** Written by lokf-docent from reader questions and consumed by the scheduled librarian: the one input that can originate from someone with no repository access and reach an agent whose output is applied with `contents: write`. The skill resolves only the question or disagreement an entry names, from the source it points at, never from the entry's own wording, so an entry phrased as a directive is read as the content it reports.
- **Fetched sources (lokf-curator).** The curator opens each concept's `resource` or `sources` and quotes it to a person before any verdict is recorded. Whatever a source contains is text to quote, never instructions, and the verdict is always the person's ("does the source still say this?"), never the agent's own "looks consistent". An adversarial source can be quoted at someone; it cannot get itself accepted.
- **Fetched sources and the repository (lokf-docent).** Verifying an exact value, or falling back once the bundle has no answer, means opening something the skill did not author: text to quote or summarize, never instructions. Docent is read-only on `.lokf/knowledge/`, and its one write path, `.lokf/feedback.md`, requires asking once per session first - never silent, never automatic.
- **Blast radius if a guard fails.** The only unattended write path is `knowledge-librarian.yaml`'s `publish` job, and enforcement lives there, on a clean checkout the agent never shared. Before applying the `refresh` job's patch it re-derives the touched paths from the patch's own `git apply --numstat` and refuses anything outside `.lokf/knowledge`, `knowledge_bundle` and `.lokf/feedback.md`, and separately refuses a patch that adds a `by: human:` claim; commits stage those three pathspecs only. The wrapper's own post-run check in `refresh` is a fail-fast convenience, not the backstop: an agent sharing that workspace could in principle blind it by poisoning `core.fsmonitor` or `core.hooksPath` (the wrapper snapshots and restores `.git/config` and `.git/hooks` around the agent call for exactly this reason) or truncate the running script (which is why its checks live in a `main()` called last). The result is a pull request that never pushes to `main` and never auto-merges; merging it is a human decision like any other change.

**What this does not cover.** Ordinary repository content the librarian scrapes while building concepts - READMEs, docs, code - has no per-entry guard: it relies on the review-before-merge every change to `main` goes through, a materially higher trust level than unreviewed reader feedback. A reader's own phrasing to lokf-docent is likewise not filtered by anything here; that boundary belongs to the agent harness running the skill, not to a Markdown instruction file. Nor does any of this make a repository a sandbox: a compromised runner, upstream action or agent harness is out of reach, and a finding in one of those should still be reported to the affected repository, with scope and reproduction.
