# Threat model

[`knowledge-trust-ladder`](https://github.com/noelmcloughlin/knowledge-trust-ladder), [KTL Registrar](https://github.com/noelmcloughlin/obsidian-ktl-registrar) and [KTL Curator](https://github.com/noelmcloughlin/obsidian-ktl-curator) run the same scheduled agent from the same `ktl-sidecar` templates and release the same way, so they share one threat model. This page is it. Each repository's `SECURITY.md` says how to report, what that repository owns, and what it inherits from here.

Two facts shape everything below. The skills are prose executed by whichever LLM agent runs them, so anywhere a skill sends the agent to read content it did not author is a prompt-injection surface. And the bundle's central trust signal, a `verified` event whose actor starts with `human:`, is a string in a Markdown file that any writer can type.

## Interactive use: scope is advisory, not enforced

A skill's `Scope:` line ("owns only `.lokf/`") is prose, not a checked permission. The Agent Skills format has no manifest for that, and an agent run interactively has whatever tool access your harness already grants it; `npx skills` prints the same warning after every install. Only the scheduled `knowledge-librarian.yaml` enforces its scope, because nothing is watching it run. Interactively, review what the agent changed before you commit or merge. That is the discipline the scheduled path's mandatory pull-request review provides automatically.

## Repository hardening

What every repository does, and why. Each `SECURITY.md` says which of these its repository carries.

- **Actions pinned to commit SHAs** in every workflow and in the three templates under `skills/ktl-sidecar/templates/github/`. Dependabot bumps the workflow pins. The templates are bumped by hand, since Dependabot scans only `.github/workflows/`.
- **`permissions: {}` at the top of every workflow**, and harden-runner in audit mode on every job that installs packages or runs third-party code.
- **The librarian runs in two jobs so the agent and the write token never meet.** `refresh` runs the agent with `contents: read` and no git credential on disk, and hands its change on as a patch. Only `publish`, which runs no agent code, can write. What each job checks is under [Prompt-injection guards](#prompt-injection-guards).
- **The agent step runs the reviewed, in-repo wrapper**, never a repository variable's content as a command. `AGENT_CLI` chooses which agent, `KNOWLEDGE_LIBRARIAN_ENABLED` arms it, and the workflow triggers only on `schedule` and `workflow_dispatch`. The agent's credential is the `AGENT_API_KEY` secret or, with `AGENT_USE_JOB_TOKEN`, the job's own token, which holds `contents: read` and `copilot-requests: write` and expires with the job. The wrapper exports it only into the agent's environment, under the name `AGENT_API_KEY_ENV` gives, and refuses a name that is not a credential's or that `gh`, git or the runner also read.
- **The release workflow packs the bundle and the write token uploads it, in separate jobs.** `knowledge-release.yaml`'s `pack` job installs the lokf toolkit and validates under `contents: read`. Only `attach`, which runs no third-party packages, holds `contents: write`, and it checks each zip, the bundle's and any Copilot skill's, against the checksum `pack` made before uploading it.
- **Every workflow write to `main` sits behind the `release` GitHub Environment.** Its required reviewers must be configured by hand, or the gate exists in name only. Release tooling is installed with `npm install --ignore-scripts`.
- **`main` blocks deletion and force-pushes and requires linear history, and no more.** A rule requiring pull requests or passing checks would also reject the release job's own push ([how the repositories release](releasing.md#what-the-repository-settings-mean-for-you)).
- **Secret scanning and push protection are on.** They are GitHub settings nothing in CI can assert, so keeping them on is a maintainer responsibility.
- **CodeQL and dependency review are off where there is nothing for them to scan.**

## Human attribution: `human:` is a claim, not a credential

A `verified` event whose actor starts with `human:` says "a named person checked this concept against its source". Everything downstream keys off it: `ktl-curator`'s health line, `ktl-docent`'s answer footers, and the OKF trust tiers themselves. It is also just a string in a Markdown file. Any writer can type one, and `lokf validate` accepts it, because a forged event is perfectly well-formed. The realistic threat is not an outside attacker but the ordinary shape of agent work: **another agent** driving `ktl-curator` and recording confirmations nobody gave. That agent may be an orchestrator, a subagent, a scheduled run, or a session where the "person" answering is really a tool result. An identity resolved from the local environment cannot tell that from a real session, because both arrive through the same channel.

Four measures, in descending order of weight:

- **The forge is the authority.** The forge is GitHub, GitLab or Forgejo. On each pull request, the `provenance` job in `knowledge-registrar.yaml` collects the actor of every `human:` event added or changed under `.lokf/knowledge/`, whether a `verified` entry or the `generated` record. It reads the frontmatter whole, against every parent of a commit, keyed by the concept's `id`: a re-dated event counts; a renamed concept, a merge and an example in a body code fence do not. It then requires evidence GitHub holds: an approving review from that account, or that account's verified signature on the commit that introduced the event, since GitHub blocks approving your own pull request. This is the only measure a confused or adversarial writer cannot decline to follow, because it runs outside the agent. Where GitHub is not the forge, or as a second opinion where it is, `knowledge-provenance.sh` does the signature half with plain git and gpg or ssh-keygen, against public keys the repository carries under `.lokf/curators/`, one GPG or SSH key per curator id. It refuses a change that adds an id's key and that id's confirmation together.
- **`ktl-curator` writes `human:` only for an authenticated identity**: `gh api user`, `glab api user`, or a signing key the forge lists under the login the person states. Never a typed name on its own. The `git config user.name` fallback, a writable config value, and the "just ask" fallback, the one channel an attacker fully controls, are gone. Without an authenticated id, the two verbs that assert a person vouched for something are refused; the three that assert nothing about who checked what stay available.
- **`ktl-curator` refuses to run a review session unattended**: in CI, headless, as a subagent, on a schedule, or with answers arriving from a file or a tool result rather than a live turn. Its read-only report is safe to run anywhere.
- **Detection, not only prevention.** The curator's report counts `human:` events whose introducing commit carries no signature, so one that arrived by another route is visible to the next person who looks instead of silently trusted.

**Limits.** A signature proves a key holder made a commit, and an approval proves an account clicked a button. Neither proves anyone read the source. The gate raises forgery from "type four lines of YAML" to "control that person's GitHub account or signing key". It does not make a confirmation true. Where `.lokf/` is gitignored, no pull request ever carries the bundle, so the CI half never runs; there, the curator's in-session rules are the whole of it. A host with no git at all has only its platform's version history. The curator names that as the record, and the report says so every time.

**The optional `attestation` job** is off unless `KNOWLEDGE_CURATION_ENVIRONMENT` names an environment. It exists for repositories that cannot sign. It is not a switch that disables the check, since a permanent "provenance: off" gets flipped once and never back. It is a fresh, logged approval from an environment reviewer on each affected pull request. One misconfiguration matters: naming an environment whose **required reviewers** are empty makes it self-approve instantly, turning the gate into a false assurance. Configure the reviewers first.

## Prompt-injection guards

The four skills read content they did not author: repository files, external URLs, reader questions. They either act on it or hand it to a person. Each skill's `SKILL.md` carries the guard for its own input path; this is the map.

- **`.lokf/feedback.md` (`ktl-librarian`).** Written by `ktl-docent` from reader questions and consumed by the scheduled librarian. It is the one input that can originate from someone with no repository access and reach an agent whose output is applied with `contents: write`. The skill resolves only the question or disagreement an entry names, from the source it points at, never from the entry's own wording, so an entry phrased as a directive is read as the content it reports. `ktl-curator` reports only how many entries wait, counted with `grep -c`, so their text never reaches its session, and `ktl-docent` adds an entry through a script rather than by opening the file, so it never reaches that one either. The librarian is the only skill that reads what a reader wrote.
- **Fetched sources (`ktl-curator`).** The curator opens each concept's `resource` or `sources` and quotes it to a person before any verdict is recorded. Whatever a source contains is text to quote, never instructions. The verdict is always the person's ("does the source still say this?"), never the agent's own "looks consistent". An adversarial source can be quoted at someone; it cannot get itself accepted.
- **Fetched sources and the repository (`ktl-docent`).** Verifying an exact value, or falling back once the bundle has no answer, means opening something the skill did not author: text to quote or summarise, never instructions. The docent is read-only on `.lokf/knowledge/`. Its one write path, `.lokf/feedback.md`, requires asking once per session first, never silently and never automatically.
- **`.lokf/feedback.md` on the way in (`ktl-docent`).** That file is kept newest first, so writing an entry used to be a read, an edit and a write back. Every earlier reader's report entered the docent's context, in the one session that has also been fetching URLs and reading repository files, and the only guard was a line of prose telling the agent not to act on them. `knowledge-feedback.sh` does the insertion instead: the skill passes its own entry as an argument and never opens the file, and the script prints only the kind, the date and a count. The guard is the call rather than a rule the agent has to keep, which is the same reason the conventions the librarian kept breaking became a script. The script closes what it can reach and no more: it holds the kind to `Miss` or `Disagreement`, the optional attribution to a forge login's characters, and the entry to one line, so a caller cannot forge a second entry or an identity. It changes nothing about the librarian, which still has to read the entries to consume them.
- **Pull-request metadata (`knowledge-registrar.yaml`).** The `provenance` job reads the pull request's number, its base and head SHAs, and the reviews and commits GitHub reports for it, which a skill scanner flags as third-party content reaching an agent. No agent runs in that job. The event fields enter through `env:`, never interpolated. The API reads are narrowed to logins, SHAs and a verification flag. The one author-controlled string, the `human:<id>` in a concept's frontmatter, is held to a login's characters before any fixed-string comparison. The token is read-only. The job does trust git's listing of changed paths, so it lists them with `core.quotePath` off and refuses a path git still has to quote.
- **Blast radius if a guard fails.** The only unattended write path is the `publish` job in `knowledge-librarian.yaml`, and enforcement lives there, on a clean checkout the agent never shared. Before applying the `refresh` job's patch it re-derives the touched paths from the patch's own `git apply --numstat` and refuses anything outside `.lokf/knowledge`, `knowledge_bundle` and `.lokf/feedback.md`. It separately refuses a patch that adds a `by: human:` claim. Commits stage those three pathspecs only. The wrapper's own post-run check in `refresh` is a fail-fast convenience, not the backstop. An agent sharing that workspace could in principle blind it by poisoning `core.fsmonitor` or `core.hooksPath`, or truncate the running script. Against the first, the wrapper snapshots `.git/config` and `.git/hooks` before the agent call and restores them from an `EXIT` trap, so an agent that fails or a job that is cancelled restores them too. Against the second, its checks live in a `main()` called last. The result is a pull request that never pushes to `main` and never auto-merges; merging it is a human decision like any other change.

**What this does not cover.** Ordinary repository content the librarian scrapes while building concepts, such as READMEs, docs and code, has no per-entry guard. It relies on the review-before-merge every change to `main` goes through, a materially higher trust level than unreviewed reader feedback. A reader's own phrasing to `ktl-docent` is likewise not filtered by anything here; that boundary belongs to the agent harness running the skill, not to a Markdown instruction file. Nor does any of this make a repository a sandbox. A compromised runner, upstream action or agent harness is out of reach, and a finding in one of those should still be reported to the affected repository, with scope and reproduction.
