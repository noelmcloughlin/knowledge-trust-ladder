# The docent in Microsoft 365 Copilot

**ktl-docent-m365** is the docent as a custom skill for a Microsoft 365 Copilot declarative agent. It is not a fifth skill. It puts ktl-docent into Copilot.

Copilot runs skills with no repository, shell or network. So the skill carries a **snapshot** of the bundle, and the docent answers from it. Each answer names the snapshot and how far each concept has been trusted. The docent cannot check a source or write `.lokf/feedback.md`, so it says so and gives the reader a gap report to file.

## Get the skill

**From a release.** Open the repository's Releases page on GitHub. Under a release's Assets, download `ktl-docent-m365-<tag>-<repository>.zip`. That is the skill, built from the bundle as that release shipped it. Nothing to install.

The release workflow attaches it beside the bundle zip, on every release whose bundle changed. A repository that has not laid down `.lokf/m365/` attaches the bundle zip alone.

**Or build it.** A repository on another forge, or on none, runs the same builder the release workflow runs, on its bundle folder:

```bash
.lokf/m365/knowledge-m365.sh --repo-url https://github.com/me/my-repo --ref v1.2.0 .lokf/knowledge ./dist
```

It creates `dist/ktl-docent-m365/`, with `SKILL.md`, `SNAPSHOT.md` (repository, revision, build date) and `knowledge/`, and `dist/ktl-docent-m365.zip`. In a git clone only tracked files are copied, and hidden files such as `.obsidian/` are left out. With `SOURCE_DATE_EPOCH` set, one input gives one zip. The build writes nothing and exits 1 if a skill breaks one of Copilot's limits: `SKILL.md` over 20,000 characters, folders more than 3 deep, file types Copilot does not accept, more than 350 files, more than 10 MB, or symbolic links.

## Add it to an agent

**With Agent Builder, nothing installed.** In Microsoft 365 Copilot, create an agent or open one you own in Agent Builder, and add the zip as a skill. Microsoft's page on [custom skills in declarative agents](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/declarative-agent-skills) shows where. Agent Builder takes the skill as one zip.

**With the Agents Toolkit, for developers.** This needs [Node.js](https://nodejs.org/) and a Microsoft 365 account that may add agents.

1. Install the [Agents Toolkit CLI](https://learn.microsoft.com/en-us/microsoftteams/platform/toolkit/microsoft-365-agents-toolkit-cli): `npm install -g @microsoft/m365agentstoolkit-cli`, then `atk auth login m365`.
2. Create an agent, or use one you have: `atk new -c declarative-agent -n my-docent -i false`.
3. Add the zip. The command is hidden unless `ATK_FRONTIER` is set to `true`:

   ```bash
   ATK_FRONTIER=true atk add skill --from ./ktl-docent-m365-v1.2.0-my-repo.zip -i false
   ```

4. Run `atk validate`, `atk provision` and `atk preview`.

Custom skills are in preview. Your tenant must be in the Frontier program, and an agent cannot have both skills and embedded files yet.

## Keep it current

The snapshot does not update itself. After each release that changes the bundle, take the new zip and add it again. The workflow packs the skill only when the bundle changed, so a release that brings new instructions and the same bundle carries no new zip; run the workflow by hand with `force` for that tag.

## One pattern for every read-only role

A Copilot skill here is an instructions file plus the snapshot. `.lokf/m365/` holds one instructions file per role, named after the skill it becomes, and the builder packs each into its own zip. The docent is `ktl-docent-m365.md`. The auditor, the third line in [three-lines.md](three-lines.md), arrives as `ktl-auditor-m365.md` beside it, and nothing else changes: not the builder, not the workflow, not the checks.

## Why not the curator yet

The librarian and the sidecar need a repository and a shell. The curator could follow when two things exist: an action that lets the agent write to SharePoint, and a way to record who confirmed what without a forge login. The shape of that record is held in reserve in the curator's [domain-schemas.md](../skills/ktl-curator/references/domain-schemas.md), unbuilt until something writes it. What Copilot allows, what the toolkit checks, and how the curator's needs map to Microsoft 365: the sidecar's [references/m365.md](../skills/ktl-sidecar/references/m365.md).

## Change the instructions

Edit [ktl-docent-m365.md](../skills/ktl-sidecar/templates/m365/ktl-docent-m365.md), which the build packs as the skill's `SKILL.md`. It is named after the skill, not `SKILL.md`, so installers don't list it as one. Its trust labels must match ktl-docent's, and the repository checks enforce that. A host's copy under `.lokf/m365/` is what its releases pack, so a host that edits it changes what its readers' Copilot follows, the same way it owns its bundle.
