# Scheduled librarian task (Karpathy rule) - operating manual

**Everything here assumes `.lokf/` is git-tracked** (ktl-sidecar's Step 0). If it's gitignored, don't scaffold or rely on any of this: `knowledge-registrar.yaml` never triggers, since nothing under `.lokf/**` is ever part of a PR diff, and `knowledge-librarian.yaml`'s change-detection step (`git status --porcelain -- .lokf/knowledge`, in the workflow) silently reports no changes for an ignored path - not a failure you'd notice, just a scheduled job that quietly does nothing, forever. Get periodic freshness in that mode from a scheduler that isn't gated on git history instead - cron, a systemd timer, or just re-running this skill by hand.

Keep the graph continuously accurate rather than rewriting it in bursts. Three pieces automate this rebuild loop - the **ktl-sidecar** skill's Step 5 scaffolds them from `../../ktl-sidecar/templates/` (`github/*.yaml`, `scripts/knowledge-librarian.sh`); this file is their operating manual:

**`.github/workflows/knowledge-librarian.yaml`** - the rebuild workflow. Runs weekly (Mondays, 05:00 UTC) and on demand (`workflow_dispatch`). Each run: a read-only `refresh` job checks out full history -> sets up `uv` -> installs the `lokf` sidecar -> runs the agent -> validates -> diffs `.lokf/knowledge/` (only the bundle, so tool artifacts never trigger a PR) -> if anything changed, packages the change (`.lokf/knowledge/` plus `.lokf/feedback.md`, ktl-docent's reader-feedback file, so entries the librarian consumed don't return) as a patch artifact; a separate privileged `publish` job then applies it on a clean checkout, commits it to a fresh `knowledge-librarian/<date>-<run_id>` branch, and opens a review PR via `github-script`. Guardrails: the agent runs in a `contents: read` job with no persisted credentials, and only the `publish` job (which runs no agent code) holds `contents: write` + `pull-requests: write`; it never pushes to the default branch, never auto-merges, and opens no PR when nothing changed. A no-change run must leave the bundle byte-for-byte untouched, including `log.md` (section 1's log policy). The PR body ends with a **For the curator** section - counts of drafts, open questions, and person-confirmed concepts, computed by the workflow from frontmatter with `grep`, not taken from the agent's output - pointing the reviewer at the **ktl-curator** skill. It is a nudge; the curator's own report is the authoritative view.

**`.lokf/scripts/knowledge-librarian.sh`** - the agent wrapper the workflow invokes directly (a fixed, reviewed path). Set the `KNOWLEDGE_LIBRARIAN_ENABLED` repository variable to `true` to arm the run and set `AGENT_CLI` to your non-interactive agent command. Put the agent's key in the `AGENT_API_KEY` secret and name the variable the agent reads it from in `AGENT_API_KEY_ENV`, such as `ANTHROPIC_API_KEY`; the wrapper hands the key to the agent under that name only. The script selects the ktl-librarian skill, builds a prompt telling the agent to follow it and re-scrape the repo, then calls `AGENT_CLI`. Its contract: it edits **only** files under `.lokf/knowledge/` and performs no git/PR operations - the workflow owns branch/commit/PR. If `KNOWLEDGE_LIBRARIAN_ENABLED` is not `true`, the workflow's agent step is skipped, so the workflow is harmless until you wire the agent up.

**`.github/workflows/knowledge-registrar.yaml`** - the gate: named for the registrar's job (keeping records well-formed and provenanced, never judging whether their content is true - a different job from this skill's own). Its `pull_request` trigger does **not** fire on the librarian's own PR: GitHub does not start `pull_request`-triggered workflows for a pull request opened with the default `GITHUB_TOKEN`, which is how `publish` opens it (a deliberate anti-recursion rule, not a bug here). So `publish` carries the two checks that matter for this PR itself, before it ever opens it: every changed path falls inside the bundle (re-derived from the patch's own `git apply --numstat` output against an allow-list, since the `refresh` job's own boundary check shared a workspace with the agent and so can't be trusted alone), and the patch adds no `by: human:` claim (this skill never writes one). To get `knowledge-registrar.yaml`'s own `validate`/`provenance` checks to run and show green on the librarian PR - useful if your branch protection requires them - close and reopen the PR, or push an empty commit to its branch; either is a human action and fires a fresh `pull_request` event. A curation PR from ktl-curator, opened normally by a person, triggers the gate immediately with no extra step - that's what `provenance` exists for. The bar: the projected RDF graph should always describe the repository as it is *today*.
