# Microsoft 365 Copilot as a host

Copilot runs a custom skill in a sandbox: no repository, no shell, no network, no package install. A skill is a folder with a `SKILL.md` whose frontmatter names it, plus any files beside it, and the model reads those files when the task calls for them. That fixes what each KTL role can be there.

| Role | On Copilot | Why |
| --- | --- | --- |
| docent, auditor | a **snapshot skill**: the role's instructions plus a copy of `knowledge/` | they only read; the bundle travels inside the zip |
| sidecar, librarian | nothing | they need a repository and a shell |
| curator | nothing yet | it needs a write action the agent can call, and an identity that is not a forge login; see below |

The sidecar lays down `.lokf/m365/`: one instructions file per read-only role, named after the skill it becomes (`ktl-docent-m365.md`), and `knowledge-m365.sh`, which packs the bundle once per file. The release workflow attaches each zip beside the bundle zip, so a person with nothing installed downloads it and uploads it to Agent Builder. How a person gets and adds it: [docs/m365.md](https://github.com/noelmcloughlin/knowledge-trust-ladder/blob/main/docs/m365.md) in this skill's home repository. A host with no git runs the builder by hand on its bundle folder ([portability.md](portability.md)).

## What Copilot allows

From Microsoft's page on custom skills, preview as of 2026-09:

- `SKILL.md` instructions under 20,000 characters; the frontmatter `name` equals the folder name and matches `^[a-z0-9]+(-[a-z0-9]+)*$`; `description` is 1 to 1024 characters.
- Folders at most 3 deep, 350 files across an agent's skills, 8 skills per agent, a 10 MB app package (the toolkit) or a 50 MB zip (Agent Builder).
- Files of the listed types only: Markdown, text, Office, PDF, images, JSON, YAML and the like. No `.toml`, no extensionless files, no links.
- Scripts may ship, but run with no network and no packages beyond the sandbox's own. They cannot call Graph, connectors or MCP; only the orchestrator can.
- The tenant must be in the Frontier program; an agent cannot mix skills with embedded files; tenants with Information Barriers have no skills; Partner Center takes none yet.

The builder refuses a result over these limits before anything ships.

## The toolkit, checked against its source

`@microsoft/m365agentstoolkit-cli` (`atk`), `dev` branch, 2026-09-24:

- `atk add skill` is hidden until `ATK_FRONTIER=true` is set, and works only inside a project the toolkit scaffolded (`m365agents.yml` present).
- `--from` takes a zip from any path; a folder only from inside the project's `appPackage/`. A zip holds one top folder, or `SKILL.md` at its root.
- The command checks the frontmatter and the name. The limits above are the service's, so passing the command proves the package is well formed, not that the skill runs.
- The skill is registered in `declarativeAgent.json` under `agent_skills`; `--expose-to-copilot` adds it to the Teams manifest's `agentSkills` too.

Agent Builder, in Microsoft 365 Copilot, takes the same zip as an upload with no CLI, which is the route for a person with nothing installed.

## The curator, when its turn comes

Git is one implementation of what the curator needs, not the need itself. On Microsoft 365 the parts map, with one gap:

| The curator needs | Git gives | Microsoft 365 would give |
| --- | --- | --- |
| a workspace root | the repository | a drive and a folder item |
| the revision a verdict was checked against | a commit hash | item id, version, ETag, and a content digest |
| who the person is | the forge login `gh` is signed in as | the Entra tenant and user object ids from a delegated `/me`, never a typed string; a display name only as a snapshot |
| a record that it was them | the signed commit, or the pull-request approval the gate reads | version history and audit metadata: attribution, not a signature; a signature needs a separate attestation service |
| a way to write the verdict | the skill's shell | an action the agent can call; the SharePoint capability reads and searches only |

Identity becomes a level of assurance rather than a precondition: `attested`, `delegated-me`, `directory-lookup`, `platform-history`, `unverified`, `anonymous`, resolved in that order from the host down, and a verdict with no identity is recorded as unverified rather than refused. The frontmatter shape for all of this is held in reserve in the curator's [domain-schemas.md](../../ktl-curator/references/domain-schemas.md), unbuilt until something writes it. What blocks the build is the last row: no write action exists yet.
